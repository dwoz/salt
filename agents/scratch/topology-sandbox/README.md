# topology sandbox

Smoke-test harness for the master-topology feature: 2 clusters (east
+ west), 2 minions per cluster, all in docker.

## layout

```
topo-east             topo-west             <-- peered via topology_link_port=4515
  topo-east-minion-1    topo-west-minion-1
  topo-east-minion-2    topo-west-minion-2
```

East's `topology.conf` names west as a peer; west's names east.  Each
master's `master_identity.{pub,pem}` keypair is generated by `up.sh`
and each cluster's `pub` is pre-copied into the other's accepted-peers
dir (`pki/<local>/masters/<peer>.pub`) -- mirrors `salt-key -a <peer>
--master` done out-of-band.

The salt source tree is bind-mounted into every container at
`/app/salt`, so code edits on the host take effect on the next
`docker compose restart <service>`.

## usage

```
./up.sh      # build, start, wait for ready
./smoke.sh   # run a handful of local + cross-cluster publishes
./down.sh    # stop (preserves PKI)
./down.sh --wipe  # stop + delete PKI (fresh identities next up)
```

### manual exploration

```
# local-cluster publish
docker exec topo-east salt '*' test.ping

# cross-cluster publish via compound matcher
docker exec topo-east salt -C 'C@west' test.ping

# minion-side grain shows which cluster the minion is in
docker exec topo-east salt '*' grains.item master_cluster_id

# follow logs
docker compose logs -f topo-east
docker compose logs -f topo-west
```

### iterating on code

1. edit a file under `salt/` in the worktree
2. `docker compose restart topo-east topo-west`  (minions keep running)
3. re-run `./smoke.sh` or your targeted command

## topology shape

```
east ──────peer────── west
  │                    │
 peer                 peer
  │                    │
east-sub            west-sub
```

Four clusters, six minions.  Only direct peering between adjacent
clusters -- `east-sub` and `west-sub` are not peered with each other,
so `west → C@east-sub` has to transit through `east`.

## known gaps (4-cluster surface more than 2-cluster)

The 2-cluster subset (east, west) passes the first ~10 smoke checks
reliably on fresh boot.  Adding sub-clusters surfaces real
implementation gaps you'll see as `salt-key -L` failures or
`SaltReqTimeoutError: Message timed out` in the master log:

1. **east↔west handshake isn't fully reliable under 4-cluster load.**
   After `./up.sh` on a fresh boot, east and west occasionally fail
   to maintain the topology link -- east's outbound `topology/pub`
   sends to west timeout with `SaltReqTimeoutError`.  east↔east-sub
   and west↔west-sub appear to come up more reliably.  The REP
   socket in the inbound listener may be getting stuck under
   concurrent connects from multiple peers.
2. **Transit routing (west→east→east-sub) is not wired yet.**
   west's router shows `route_publish flooding --- no known route
   for destination(s) ['east-sub']` because west has no summary gossip
   from east about east-sub's membership.  west falls back to flood
   through east, which also depends on gap #1.
3. **The handshake's `pub channel connect skipped: ...NoneType`
   warning** fires on every outbound connect -- a latent bug in the
   outbound pub channel setup that doesn't yet break the REQ-REP path
   but is a red flag.

For now the sandbox is most useful at **2-cluster scope**: run
`./smoke.sh` and look at the "global `*` publishes" and "scoped
C@<peer> publishes" sections, which exercise the three fixes we
landed (Issues 1-3).  The sub-cluster / transit sections won't pass
until gaps 1-3 above are closed.

## gotchas

- `topology_link_port: 4515` is the same number on both masters -- each
  binds the port on its own container, so there is no collision; the
  peer address in `topology.conf` uses the other container's hostname.
- `auto_accept: True` for minions and pre-populated master-peer keys
  are **sandbox-only** shortcuts.  In production you accept each
  manually via `salt-key -a` (minions) / `salt-key -a <cluster_id>
  --master` (peers).
- The cross-cluster publish currently waits the full `--timeout` (5s
  default) because the origin master cannot know peer-cluster minions
  at pub-time.  See the follow-up note in
  `rfcs/diag-transport-wire.md` section 4.
- PKI material is held under `./pki/<role>/` and bind-mounted into
  each container.  Running containers as root inside the container
  means the PKI dirs will be owned root on your host after they boot.
  Not a concern for a sandbox.
